# 阶段驱动开发规范

这是一套适合 yucli 的轻量 SDD（Specification-Driven Development）流程。它的目的不是增加文档工作，而是让每个 Agent 能力都先有明确行为，再有可追踪的实现和验证。

## 阶段是什么

阶段是一个用户能够观察和验证的完整能力，例如“单次模型问答”或“读取文件并回答”。阶段不应只描述内部重构，也不应一次包含多个没有依赖关系的能力。

每个阶段有一个主文档：

```text
docs/specs/phase-XX-<short-name>.md
```

它同时记录设计和结果，避免需求、设计和实现记录分散后互相失真。

## 阶段文档的固定内容

1. **状态与目标**：当前状态、用户场景、完成后的可观察行为。
2. **范围**：本阶段包含什么，明确不做什么。
3. **验收场景**：用输入、动作、预期结果描述成功和失败路径。
4. **调用链与状态**：谁调用谁，数据怎样流动，状态由哪个模块拥有。
5. **数据与接口**：消息、请求、响应、工具或存储契约；复杂契约链接到 `docs/contracts/`。
6. **设计选择**：重要取舍链接到 `docs/decisions/`。
7. **任务清单**：按依赖顺序拆分成小任务，每项能单独检查。
8. **验证计划**：类型检查、单元测试、集成测试、CLI 冒烟或人工检查。
9. **实际结果**：完成的任务、运行过的命令、结果、未解决问题和下一步。

阶段开始时先填写前八项；实现过程中更新任务和决策；验证结束后补第九项并将状态改为 `done`。如果范围变化，应先修改范围和验收，再继续代码，不能只在实现后补一句说明。

## 用户提出开发请求时的协作方式

当用户说“开发阶段 X”或给出一个阶段目标时，助手先提供一份简短的阶段开发说明，至少包括：

- 要解决的用户问题和完成标准。
- 当前代码会新增或修改哪些模块。
- 关键数据结构和调用顺序。
- 成功、失败、取消和资源边界。
- 要更新的阶段文档、契约文档和 ADR。
- 分步任务与验证命令。

如果这些内容已经在阶段文档中确定，就直接引用并进入实现；只有出现新的行为选择、范围变化或高风险副作用时才请求用户决定。用户要求“先设计”时，只更新设计，不实现代码。

阶段文档不应留下没有方向的空白选择。对每个会影响实现的选择，采用以下规则：

- 低风险、容易撤销的选择由助手直接决定，并写明默认方案和理由。
- 会影响协议、依赖、数据格式、费用、安全或后续阶段的选择，在阶段规格中给出推荐方案和必要的备选方案供用户选择或修改；决策一旦确定，ADR 只记录最终采用的方案、理由和影响。
- 如果用户没有特别指定，推荐方案就是实现依据；不把“待确认”当作暂停实现的通用理由。
- 用户修改默认方案后，先同步阶段文档、契约和 ADR，再实现受影响的代码。

## 接口和架构文档如何维护

### 接口契约

跨模块接口、消息结构、工具输入输出和持久化格式放在 `docs/contracts/`。契约至少说明：调用方和实现方、字段含义、成功结果、失败结果、取消/超时行为、兼容性要求和示例。

代码中的 TypeScript 类型是可执行约束，契约文档是面向设计和审查的说明；两者不一致时先修正设计，再同步代码和测试。

### 架构文档

模块职责、主数据流和生命周期变化更新 `docs/architecture.md`。局部实现细节留在代码和阶段文档中，避免架构文档变成所有文件的索引。

### 架构决策

当选择会影响后续阶段，例如模型协议、会话格式、并发策略或持久化方案，新增一个 `docs/decisions/ADR-XXX-<name>.md`。小的实现选择不需要 ADR。

## Git 与阶段的强制关系

阶段分支和 Git 提交是强制流程，适用于代码、测试和文档。阶段规格、接口契约、ADR、架构文档和开发报告都必须和对应的阶段变化一起进入 Git；不能只提交代码而把设计文档留在工作区，也不能只改文档而不留下提交记录。

阶段的 Git 边界：

```text
main
  ↓ 创建阶段分支
phase/XX-short-name
  → 阶段文档 → 设计调整 → 实现与测试 → 验证记录
  ↓ 审查通过后合并
main
```

开始任何阶段工作前，必须确认：

1. 当前位于阶段分支，例如 `phase/01-single-model`。
2. 阶段规格、契约和 ADR 的当前版本已经在该分支中。
3. 如果仓库还没有任何提交，初始化内容先提交到第一个阶段分支；首次集成到 `main` 仍然等待用户授权。

阶段中的文档和代码都要提交。提交信息说明具体变化，例如：

```text
docs: define phase 1 single model contract
feat: add non-streaming llm client
test: cover model request failures
```

阶段分支上的小步提交属于阶段开发的一部分，助手可以在已授权范围内自行创建。阶段完成前必须检查工作区干净、测试和验证结果已记录、阶段文档状态为 `verified` 或 `done`，然后停在阶段分支，等待用户授权合并回 `main`。助手不得未经授权向 `main` 提交、合并、推送、创建阶段标签或删除分支。

## Agent 开发报告

yucli 当前采用两个长期角色：项目规划 Agent 和开发 Agent。项目规划 Agent 负责阶段文档、契约、ADR、验收和审查；开发 Agent 只负责依据已确认文档实现代码、测试和必要的实现细节。

开发 Agent 在一个阶段的实现结束时提交一份开发报告。报告写在 Agent 的最终回复中即可，不要求为每个小任务新增永久文件。格式统一使用[开发报告模板](templates/development-report.md)。

项目规划 Agent 收到报告后检查工作区和验证结果，并把有长期价值的内容同步到阶段规格、接口契约或 ADR。阶段完成时只维护一份阶段汇总，不把开发报告原样堆进项目文档。

如果开发 Agent 发现实现需要改变已确认的设计，应先在报告中标明冲突和影响，由项目规划 Agent 更新设计后再继续。阶段报告以阶段为单位；只有在明确拆分成多个独立开发 Agent 时，才分别报告各自负责的部分。

## 完成定义

一个阶段只有同时满足以下条件才标记为 `done`：

- 验收场景已经有实际验证结果。
- 代码、类型、契约和架构文档相互一致。
- 失败路径和限制已经记录。
- 必要测试和 CLI 冒烟检查通过，未运行的检查明确标出。
- 下一阶段的前置条件和遗留问题已经写清楚。
